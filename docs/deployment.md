# Deployment and activation handoff

## Ethereum launch

The network's factory deploys **one** application: `WishGarden`, nonpayable constructor `(address owner_)`, with `0x48E4E74fE1d0c14404cEB57B9fec5b21329C6ec9`. Constructors make no external calls and work on an empty chain. Treasury and bridge queue are abstract inherited logic. Do not deploy the obsolete sink/treasury, a launch token, NFT, pool, proxy, or Base receiver on Ethereum.

[manifest-handoff.json](deployment/manifest-handoff.json) supplies the constructor and ABI reference for the later manifest step. There is no builder-written `launch.json`. The network supplies the accepted source commit, GitHub publication, final manifest, factory deployment, explorer verification, address and deployment receipt after review. No source publication or deployment has been performed by this contribution. Do not invent an address or reuse either legacy contract.

After deployment check owner, chain 1, bytecode/source match, no linked libraries, `activated() == false`, `purchasesPaused() == true`, and zero candle/financial totals. Archive the service-confirmed address/ABI/source revision and transaction receipt. No initialization call by the factory is needed or expected.

## Activation blockers and ordered owner steps

Purchases must remain disabled until **all** of these steps are complete. The interface/address facts below are known; deployment-specific values and current configuration still require verification. This is an allowed later owner setup, not missing worker deployment credentials.

1. Complete independent network review of the final source and manifest. The local model/adversarial tests are evidence, not an independently signed audit approval.
2. Obtain the confirmed Ethereum garden address. Use the [Base package](base/README.md) to deploy `EverlightBurnReceiver(owner, ethereumGarden)` on **Base 8453** with the same named owner. Keep it outside Ethereum's manifest. Verify source, constructor arguments, runtime and reciprocal garden address. No new IMD token is deployed.
3. Reverify current Ethereum IMD, Base adapter and Base token code against [evidence](evidence/bridge-dependencies.json). The fixed LayerZero endpoint is `0x1a44076050125825900e736c501f859c50fE728c` on both chains; Ethereum EID 30101, Base EID 30184. Check endpoint code/EID and official peers in both directions. Ethereum's token must be its own OFT, `approvalRequired()==false`, conversion rate `10^12`; Base adapter must report the supplied Base token, approval required, and the same conversion. Review enforced send-and-call options, message inspector, and bridge permissions. App configuration cannot repoint the token, adapter or endpoint.
4. Review LayerZero **current default send/receive libraries, DVNs, confirmations, executor and native-fee settings**, for the token bridge and the new Base-receiver-to-Ethereum-garden receipt channel. This receipt channel is a new application using endpoint defaults, not the token's peer configuration. The app never appoints an endpoint delegate or exposes library/config setters; if defaults do not support or safely serve this route, **do not activate**. Library/default governance remains an external trust assumption; application immutability does not freeze LayerZero or IMD administrators. These live default settings and production receipt delivery have **not been certified by this contribution**.
5. Verify Base token policy allows exact adapter-to-receiver transfers: receiver is not blacklisted or an AMM pair, trading/migration conditions permit receipt, balance including concurrent pending deliveries stays within any wallet limit, and adapter has enough unlocked collateral. The supplied token currently identifies itself as “Fren Pet”; preserve the supplied address and explicitly reconcile its branding in owner evidence. `blacklistRenounced()` was false in the live observation. A token administrator can still affect future bridge liveness. No contract can promise future availability of that external route.
6. Review the fixed execution budgets and quote both native fee legs, including the return receipt. Source self-call budget: 1,000,000 gas; Base burn self-call budget: 150,000; executor receive option 200,000; compose option 500,000; each message fee <=0.05 ETH, paid separately. Use simulations with the actual deployments and current token state; do not make real-fund test candle purchases. Prepare a reviewed evidence document containing deployment/runtime/peer/security/fee facts and hash its exact bytes with Keccak-256. The **same** nonzero evidence hash is used on both chains. No canned placeholder evidence hash is supplied.
7. On Ethereum, owner calls `configureBridge(actualBaseReceiver, evidenceHash)`. On Base, owner calls `activate(evidenceHash)`. The Base receiver freezes its configuration and snapshots local dependency code hashes; its constructor garden and fixed token/adapter/endpoint cannot be changed. Ethereum can correct its setup before activation; doing so resets readiness. If Base was incorrectly configured, replace the receiver before Ethereum activation, not after taking payments.
8. On Base, obtain `quoteReceipt(1, bytes32(0))`, then owner sends `announceReady()` with exactly that native fee. `bytes32(0)` is the protocol's **no-burn readiness message selector**, not an address or missing deployment value. Wait for canonical authenticated `BaseReadinessConfirmed` on Ethereum. Readiness proves the deployed receiver has passed its local setup and the receipt channel delivered; it is **not a live-fund burn test**. Ethereum then checks `baseReady()`.
9. On Ethereum, owner calls `activate()`. The call checks the fixed route and snapshots, freezes the receiver/evidence/options/code-hash configuration and enables purchases. Confirm `Activated` and `PurchasesPaused(false)`. Economic rates are constants from deployment. After activation configuration is irreversible; only purchases can be paused/resumed.

Source/ABI agreement and all owner decisions above are recorded in the deployment evidence. An Ethereum owner cannot inspect Base bytecode directly: choosing the reviewed receiver is an explicit pre-activation owner trust boundary. Readiness authentication proves the sender address, not arbitrary remote source-code correctness. There is no owner-set “burn complete” function.

## Operations and recovery

- Select `queueBurn(maximumAmount)` based on available queue, Base adapter liquidity and token transfer limits; query `quoteBurn(id)`, then `dispatchBurn(id)` with the exact native fee. Require `BurnDispatched` and status InTransit; a successful transaction returning false is a recorded **failed attempt**, not a bridge send.
- A Failed source job retains reserved IMD. Inspect failure evidence and dependency state, then retry `dispatchBurn` with the same ID. Do not create a replacement send for that reservation. An owner cannot reclaim it as revenue.
- A successfully sent source job remains InTransit until authenticated confirmation, including when remote delivery fails or is delayed. Use the official LayerZero executor/manual retry mechanism for the **original** packet. Never send the job a second time or mark it complete based on a block explorer screenshot or timeout.
- Base's adapter transfer and composer call are separate stages. If credit/compose has not completed, retry that original endpoint delivery. Low gas reverts before work is silently skipped. If compose recorded BurnFailed, call `retryBurn(originalGuid)` once the underlying problem is resolved; it consumes only that original amount. No recovery branch sends tokens to the owner.
- A Base burn with no source acknowledgement needs `sendBurnReceipt(originalGuid)`, funded separately. Quote it with `quoteReceipt(2, originalGuid)`. If the send reverts it is safe to retry. If it succeeded but Ethereum delivery failed, retry the existing endpoint packet. Replay guards prevent double confirmation. Confirmation requires exact ID, original OFT GUID, amount and configuration hash.
- Pause purchases when a route becomes unavailable. Claims and fee withdrawals remain available with their original accounting. Dispatch remains available while paused if the route checks still pass. External dependency changes may strand burn operations; there is deliberately no arbitrary withdrawal, alternate target, upgrade, confiscation or owner override to bypass this restriction.
- Direct IMD donations or forced ETH are not purchase revenue. There is no generic rescue/sweep. Gas is funded by the message caller, never by selling or withdrawing queued IMD.

No website, website hosting, existing garden migration or legacy treasury transaction is part of this handoff.
